## §0 判定标尺：什么算"可验证"

自嗨与硬核的分界只有一条：**能不能被一条命令推翻**。

| 级别 | 形态 | 例子 | 懂技术的人的反应 |
|------|------|------|-----------------|
| L-1 | 叙事 | "我们零成本" | 翻白眼 |
| L0 | 数字 | "我们 $11.93/月" | 嗯 |
| L1 | 可复现数字 | "这是命令输出，你自己跑" | 有意思 |
| L2 | **可证伪断言** | "这条断言有一把刀，跑一下它就死" | 认真看 |
| L3 | **自证系统** | "文档里的数字是生成的，手改 CI 就红" | 惊掉下巴 |

**本体系只接受 L2 与 L3。** 任何无法升到 L2 的想法，进入 §3 的反方法清单，而不是被包装成卖点。

## §1 第一性原理：量纲分析

一个新闻情报系统的全部开销只能落在 5 个量纲上：

| 符号 | 量纲 | 单位 |
|------|------|------|
| **R** | 请求数 | 次 |
| **C** | CPU 时间 | ms |
| **S** | 存储 | byte |
| **Q** | 数据库读行数 | rows |
| **T** | AI token / neuron | 个 |

产出只有 1 个量纲：**E = 有效事件（条）**。效率写作 `质量(E) / (R, C, S, Q, T)`。

关键洞察在**免费额度的不对称**：`R/S/Q/T` 都可以用架构绕开，
**只有 `C` 不行**——它不是预算，是单次调用的天花板。

> **推论**：唯一值得优化的方向是"让代码不执行"，而不是"让代码跑得更快"。

## §2 六条定理

> **T0｜删除定理**
> 在固定约束下，系统能力的上限由**被删除的组件数**决定，而非被引入的技术数。
> *推论：任何"加一个中间件解决 X"的提案，先回答"能不能不加，而让 X 消失"。*

> **T1｜解约定理**
> 每次请求的 CPU 时间必须与数据规模解耦。死掉的路径不是"慢"，是"读得多"。
> **优化常数是战术，消除执行是战略。**

> **T2｜读写分离定理**
> 把计算从读路径挪到写路径。写路径成本 ∝ 数据变更次数；读路径成本 ∝ 读者数。
> 把计算放在写路径，等于让读者数从成本函数里消失——
> **这是"免费资源支持超大规模"的数学证明，而不是一句口号。**

> **T3｜算术可信定理**
> 可信度必须可算术验证，不可叙事。`"便宜" = usage_api() < quota`；
> `"对等" = hash(py) == hash(ts)`；`"无漂移" = generated == committed`。

> **T4｜编译器定理**
> AI 不应在热路径上，热路径上只能有查表。**LLM 是编译器，不是解释器。**
> 任何"每次请求都调 LLM"的设计，其成本函数含 R，必然不可扩展。

> **T6｜对照定理**
> 任何"新方案更好"的断言，必须同时存在 A/B 两组的同时观测数据。
> **没有对照组，所有优化都是故事。**
> *推论：对照组不是成本，是唯一能把"更好"变成"好多少"的仪器。*

> **T5｜负债定理**
> 任何不可证伪的强断言都是技术负债。
> 没有一条命令能推翻的"生产正常""零成本""bit-for-bit 对等"，都是营销文案，
> 且会在下一次审计时变成事故。

## §3 不变量

### 3.1 全局不变量

| # | 不变量 | 校验方式 |
|---|--------|---------|
| **INV-1** | 成本函数不含读者数 | 读者边际 CPU-ms（北极星 N2） |
| **INV-2** | 结论可追溯到字节 | 任何输出可回溯到不可变原文及其 SHA-256 |
| **INV-3** | 状态不可叙述，只能测量 | "健康／对等／便宜"必须由脚本产出，且脚本可反向运行 |
| **INV-A** | `main` 任何时刻可部署、可回滚、未被实验影响 | 所有实验在 `preview` 轨道 |
| **INV-B** | 任何"更好"的结论必须有 A/B 同时观测数据 | 支配判定 (1)(2) 强制 |
| **INV-C** | 每次实验产出可复现回执 | commit + config digest + 计数 + 计时 |
| **INV-D** | **守卫必须针对真实制品测试** | 读取真实配置/schema/契约的守卫，其测试必须至少一条消费仓库中那份真实文件；合成 fixture 只能补充边界，不能替代真品 |

### 3.2 INV-D 为什么是宪法级

同一模式在 2026-09-19 的审查中出现**三次**，每次都造成数十天的静默失效：

| 实例 | 失效期 | 根因 |
|------|--------|------|
| preview 部署 | **45 天** | 配置渲染守卫的测试使用 `tmp_path` 合成 TOML，而真实 `wrangler.toml` 有 3 处占位符（守卫要求 1 处） |
| 文档规模数字 | **≥3 个月** | 文档手写数字，无任何机制校验其与磁盘一致；测试数 7 处互相矛盾 |
| `main` 部署通道 | **46 天** | 测试断言一个已被删除的 npm 依赖，而 46 天内无人执行过部署 |
| 占位 KV id | **45 天（生产全程）** | 配置里一个"看起来配好了其实没配"的值；没有任何门禁会发现它 |
| **工具入口** | 0 天（同日发现） | 单元测试直接调 `main()`，而三个命令行**完全不可执行** —— "可导入的函数"与"可执行的制品"是两回事 |

> **最后一例尤其值得注意**：它是在**同一批工作中当场发现**的，
> 且当时 35 项单元测试**全部通过**。这证明 INV-D 不是"过去犯过的错"，
> 而是一种**持续存在的失效模式**：只要验证对象不是真实制品，门禁就是装饰。

**三者都是"断言指向真实世界，但验证指向玩具世界"。** 这不是疏忽，是**结构性缺陷**，
因此升级为宪法级不变量。

## §4 红线（不做的事）

### 4.1 产品红线

| 红线 | 依据 |
|------|------|
| 不自动对外发布 | ADR-0016；`v1 止于通知` |
| 不替代人工决策 | Iron Man 套装：关键判断保留人工介入点 |
| 不做多租户 SaaS | 产品基准 §7；现有通知规则实现已损坏，不应扩建 |
| 不做双向翻译产品 | 产品基准 P6：单向（中文读者读外媒） |
| 不追流量 | 公开站是**能力展示面**，不是消费产品 |

### 4.2 工程红线

| 红线 | 依据 |
|------|------|
| 不引入新运行时依赖 | Python 侧保持 8 个；新依赖需"一进二出" |
| 不 vendor 外部项目 | ADR-0008 |
| 不引入新云服务商 | 零新增成本约束 |
| **不为叙事制造组件** | 不为"一个二进制"强行打包；不为"AI 在浏览器"假装省钱 |
| **不为秀而秀** | 任何方案必须通过"最差 5% 场景"检验（March of Nines） |

### 4.3 反方法清单（看起来硬核，实际是 Cargo Cult）

**这一节比推荐清单更重要。** 一个只会推荐的人和会拒绝的人，区别就在这里。

| 反方法 | 为什么诱人 | 为什么拒绝 |
|--------|-----------|-----------|
| **手写汇编** | "让懂技术的人惊掉下巴" | 本系统是 **IO 密集**，不是计算密集。汇编优化常数，**不能消除执行**。10ms 预算里把 8ms 压到 6ms 是战术，压到 **0ms** 是战略 |
| **向量数据库** | "AI 系统标配" | RAG 成本函数含 R。SQLite FTS5 + surprisal 打分能覆盖的场景，加 Pinecone 只是把复杂度搬进别人的账单 |
| **K8s / 微服务** | "生产级" | 全部负载是 196 次/天的定时任务 + 只读请求。K8s 解决"多团队协调部署"，本项目只有一个人 |
| **重写为 Tauri / Rust** | "性能" | 基准文档里 Tauri 的数字全是"预期"，而 pywebview 有实测。**用未测量的方案替换已测量的方案是反工程** |
| **GraphQL / gRPC** | "现代 API" | 12 条路由。REST + 一个快照 JSON 已经够用 |
| **引入测试框架依赖** | "更专业" | 300 行 stdlib 可覆盖同样的不变量。**运行时依赖是负债，开发依赖也是负债**（进入 CI 供应链面） |

**判据**：反方法清单里的每一项都是"引入组件"；本体系的每一项都是"删除组件"或"证明断言"。

## §5 对抗性审查方法论

对每一个"卖点"，构造一个**能让它死掉的输入**，然后跑。四步：

```
1. 找到卖点的载体      —— 一句文档、一个布尔值、一个注释
2. 构造致死输入        —— 能让这句话变成假话的最小输入
3. 写成一条命令        —— 必须 10 秒内跑完，输出可判定
4. 检查门禁是否存在    —— 如果没有任何 CI/脚本会因它变红，它就是负债
```

**第 4 步是关键**：没有门禁的断言必然腐烂。

本方法论的常驻实现是 [`tools/falsify.sh`](../../tools/falsify.sh)，
它对每条断言回答一个问题：**"这条断言，今天还成立吗？"**
输出 `PRESENT`（缺陷仍在）/ `FIXED`（已消除）/ `UNKNOWN`（需运行时）。

> **元规则**：本方法论必须也应用于构建方法论本身的工具。
> 实例：`falsify.sh` 的 A6 判据首版误报，正是因为复核了自己的证据行才被发现并修正。

## §6 AI 辅助设计原则

沿用 Karpathy 四项心智模型（不改动语义，仅在此登记为宪法级）：

1. **锯齿状智能**：LLM 能力非均匀分布。为已知凹陷点（数字/日期提取、跨语言实体对齐、极端情感）
   加规则兜底，不靠更大模型硬解。每个 AI 组件须附"已知失败模式"清单。
2. **Iron Man 套装**：增强人工研判，不替代。关键判断保留人工介入点。
3. **March of Nines**：Demo ≠ 部署。评估任何组件时必须问"最差 5% 场景下会怎样"。
4. **构建即理解**：用最少代码重建不出来的组件，说明还不理解它。

**决策检查清单**（出现 ≥2 个 ❌ 时方案必须重新设计）：

```
□ March of Nines:  最差 5% 场景下会怎样？
□ 构建即理解:      能向新人解释清楚核心原理吗？
□ 锯齿状智能:      依赖的 AI 能力在哪些维度可能有凹陷？
□ Iron Man 套装:    关键决策点是否保留了人工介入？
□ 简洁优先:         资深工程师会认为过度复杂吗？
```
