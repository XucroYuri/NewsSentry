## 0. 裁决后的一句话定位

> **News Sentry 是一个面向中文读者的、可自托管的多语种新闻情报工具。近期它服务于一个真实的个人专业用户（记者/研究员）；公开站是 canonical event 归并能力的展示面。商业订阅是长线目标，其启动由一个明确的触发条件支配。**

这句话的每个定语都是一条裁决，见下文。

## 2. 六条裁决（逐条）

### 2.1 生意 vs 作品 → 过渡态，触发条件显式化

**裁决**：现在是作品，商业是长线目标。**启动商业评估的触发条件是：第一个真实用户连续使用 30 天。**

**理由**：
- "付费订阅"与"没有护城河"不可共存。前者要求可防御性，后者否认可防御性。**两者之间，问卷里更可信的是后者**——它是一个 solo 开发者对自己作品的诚实判断。
- 一个没有真实用户的付费产品，没有资格谈订阅；一个没有真实用户的作品，有资格谈任何事。

**护城河裁决（唯一的例外坚持）**：四类候选护城河中，只有一类值得建——

| 候选护城河 | 裁决 |
|-----------|------|
| 时间壁垒（1125 源矩阵） | ❌ 源是 config，别人可抄；且当前 74.10% ok 率说明"积累"含大量负债 |
| 成本壁垒（$0 运行） | ⚠️ 真实但可复制；对照组实验（SPEC v2）负责证明它 |
| 网络效应（Collector Node） | ❌ 鸡生蛋，在零用户阶段谈它是幻想 |
| **信任壁垒（归并质量 + 溯源可验证）** | ✅ **唯一值得建**。它的原料是评测集 + 校准门禁 + 溯源链，别人抄不走的是"持续几年标注出来的质量" |

**推翻条件**：出现任何一封真实的付费/合作意向（书面）→ 立即重开商业评估，不等待 30 天。

### 2.2 第一个用户 → 个人专业用户，不是机构

**裁决**：第一个真实用户 = **一个具体的记者/研究员个人**（你能每周联系上、会当面告诉你"这周它帮我做了什么"的人）。机构目标是 12 个月后的第二阶段。

**理由**：
1. "智库团队"与"单人自用"矛盾——而问卷在"多用户"上选择了单人自用，说明机构的协作场景不是你真正想做的。
2. 代码证据：所谓多用户是**坏的**。`core/entity_handlers.py:272` 从认证主体取 `sub` 字段，但主体里只有 `username`（`api/middleware/auth.py:129`）→ `user_id` 永远为空串 → 所有用户的规则全局共享（`store/_rules.py:55` 的空值检查直接跳过过滤）；前端角色 `writer/viewer` 后端拒绝（`api_server.py:1902` 只认 `admin|reader`）→ 界面建用户直接 400。**服务机构的协作设施现状是从零开始，不是缺功能。**
3. 单人 + local-first 架构**恰好**匹配个人专业用户：Obsidian 草稿、CLI、自托管。

**第一步动作（本周）**：确定这个人。标准：他会当面给你反馈。**没有这个人，90 天主指标就没有载体。**

**推翻条件**：你手上有可本周联系的机构联系人 → 机构提前为第一用户，但多用户设施必须真做（§2.3 的 C 选项升级为 B）。

### 2.3 管理后台 → 最小审核 GUI，运维回归 CLI

**裁决**：管理后台从 **9 页面 / ~60 endpoint** 收敛为**两件事：审核（drafts→reviewed→published 状态机）+ 导出（Markdown 简报）**。其余（配置、诊断、用户管理、信源 CRUD、通知规则）回归 CLI 与脚本。

**理由**：
- 与"砍后台回归 CLI-first"的问卷答案方向一致，但保留**产品闭环唯一需要 GUI 的一步**——人工审核。`CLAUDE.md` 红线："v1 不自动对外发布"，审核是人与系统之间唯一的门，不能藏在 CLI 后面。
- 运维类界面（用户管理、诊断、config CRUD）的使用者是你自己，CLI 更高效且可审计。
- 工程上：admin 不进 preview 轨道的公共产品面；Container 存活期间照旧代理，**Container 删除后**（SPEC v2 L2）admin 静态化到 Pages，只保留审核/导出端点。

**不做**：修多用户 bug、做团队协作、做机构审计。**现有坏代码标记为冻结，不进 preview 基线。**

**推翻条件**：§2.2 的机构联系人提前出现 → 多用户设施真做，admin 收敛计划撤销。

### 2.4 公开站 → canonical 对比首页，feed 降为次级 tab

**裁决**：公开站首页第一屏 = **"今日最活跃的 3 条 canonical events：一条事件 × 多国信源 × 溯源链"**。完整可筛选 feed 保留为次级 tab（问卷里选择的 B 形态不删除，只是不再是第一屏）。

**理由**：
- 展示面的职责是**证明那个"别人抄不走的东西"存在**——而商业文档自己定义的核心价值就是归并与追踪（`docs/specs/2026-05-30-global-intelligence-platform-business-architecture-design.md:375-381`："更可靠地去重、归并和追踪事件"）。
- 一个新闻列表是商品，任何 RSS 聚合器都有；**"同一条事件被 5 国媒体如何报道 + 每一句结论能回溯到原始字节"才是这个仓库 42K 行代码真正长出来的能力**。
- 技术上：canonical 数据已存在（`canonical_events`、`event_mentions` 表），首页只是把它**从数据层升为产品主视觉**。这一步同时锻炼 E（信任缺口）：对比视图天然要求溯源链。
- 这个裁决直接决定 SPEC v2 L5 单 HTML 的信息架构（§5.2 重排）。

**推翻条件**：一个真实用户在 30 天使用中明确说"我要的是快速扫标题，不是看事件链" → 首页换回 feed 优先。

### 2.5 六个缺口 → 只修 B→E→C，A 只做核心层

**裁决**：放弃"82 个 target 全部达标"的补源工程，改为**分层覆盖**：

```
核心层（5 个旗舰 target）： 深度覆盖，ok ≥ 90%，source_coverage 达标
准核心层（11 个 ≥20 源）：  维持现状，随质量攻坚自然提升
标题流层（其余 70 个）：    best-effort，UI 明确标注覆盖等级，不设 SLO
```

**理由（第一性原理）**：缺口之间存在因果链，而非并列——

```
A(有料) → B(料是真的) → E(能证明是真的) → C(能交付成简报) → D(有人知道) → 付费
```

- **A 的真相**：不是"料不够"，是"广度幻觉"。按 ≥20 源口径实测有 **11 个 target 达标**（italy 56 / germany 41 / france 31 / vietnam 23 / south-korea 21 / south-asia 21 / brics 21 / united-states 20 / united-kingdom 20 / india 20 / canada 20）；项目审计口径更严（含社媒等附加条件）说 3 个。**把 78 个 target 补到达标，是 6 个月做一件没人付费的事。**
- **B 是真正的病**：ok 率 74.10%（`docs/status.md:14`），且健康会谎报 `ok`（审计记录停 9 天仍 ok）。用户不会流失于"源不够"，会流失于"你推给我的东西是垃圾/过期的"。
- **E 是付费的理由**：商业文档声称的核心价值是"可验证的归并与追踪"，而引用审计 ok 率恰是 74.10%。**B 和 E 是同一个病**：数据不可信。
- 90 天内 B→E→C 是闭环：把 5 个旗舰 target 的 ok 拉到 90% → 首页对比视图让可信度可见 → 每周期产出一份可引用的简报。

**五个旗舰的初始选择（可随用户反馈替换）**：italy、germany、france（现有源深度前三）+ 由第一个真实用户指定其余 2 个。**用户的关注范围优先于配置里的数字。**

**推翻条件**：第一个真实用户关注的国家不在核心层 → 以用户关注为准重排（这本来就是设计意图）。

### 2.6 语言 → 单向（中文读者读外媒），否决两者并重

**裁决**：产品语言方向 = **中文读者读外媒**。英文/多语页面保留为 SEO/GEO 壳（已有 locale 前缀与 `llms.txt` 服务 AI 检索），**不建设完整的反向翻译产品**。

**理由**：
- 磁盘证据指向单向：`core/public_translation.py:1-4` 的发布门槛只认**中文标题、中文摘要**；`frontend/public/index.html:11` 自述"面向中文读者"；意大利语文案仅存在于 SEO 元数据（`lib/seo/site-seo.ts:11-13`），UI 字符串是硬编码中文。
- "两者并重"的完整形态 = 双向翻译 × 1125 源 + 完整 i18n UI + 多语内容管线。在零成本约束 + solo 资源下，这是三倍工作量换一个没有证据的需求。
- 涉华（china-watch）裁决：**补建是正确方向，但排在 90 天之后**。一个空的涉华 target 只是叙事；先把 5 个旗舰的可信度做出来，涉华叙事才有地基。

**推翻条件**：第一个真实用户是外文读者 → 方向反转。

## 5. 产品原则（继承 + 新增）

继承（来自 `docs/plans/2026-06-09-public-news-productization-replatform.md:65-72` 与 Karpathy 四原则）：

- 增强人工研判，不替代人工；关键判断保留人工介入点
- 公开站的核心任务是**消费新闻**，不是解释系统如何采集
- 不把 `pipeline_stage`、裸分数等工程字段暴露到主视觉
- v1 不自动对外发布（红线不变）

**新增（本基线）**：

1. **一个用户 > 一千个潜在用户**：任何功能先回答"第一个真实用户用它干什么"，答不上来的功能不做。
2. **展示 > 功能**：公开站的每一个新增页面，第一目的是证明归并与溯源能力存在，其次才是消费。
3. **诚实分级**：覆盖层级的差异必须显式标注（核心/标题流），不许让"标题流"冒充"深度覆盖"。
4. **数字生成制**：产品指标与工程指标全部进入 `docs/generated/`，手改即 CI 红（SPEC v2 INV-D 的产品化）。
5. **删除优先**：新增任何组件（含产品功能）必须回答"删掉什么换它"。

## 6. 对 SPEC v2 的重排

产品基线改变工程 SPEC 的**优先级与范围**，不改变其结构与不变量（对照实验、支配判定、INV-A/B/C/D 全部保留）。

| SPEC v2 元素 | 原排序 | **重排后** | 原因 |
|-------------|--------|-----------|------|
| L0 真相层 | 第一 | 第一（不变） | 产品事实基线（§3）并入 `metrics.json` |
| L1 对照仪器 | 第二 | 第二（不变） | G0 硬前置不变 |
| L2 实验组上线 | 第三 | 第三，但采集范围改为**仅 5 个旗舰 target** | 与分层覆盖裁决一致；对照实验在核心层先跑通 |
| E1–E3 对照实验 | — | 不变 | 工程不变量 |
| **E4（前端制品）** | 工程项 | **升级为产品主线** | 展示面 = canonical 首页，单 HTML 承载 §2.4 的信息架构 |
| L3 确定性智能 | 第四 | 第四，**优先级上调** | 校准门禁 = 信任壁垒的算术基础（§2.1） |
| L4 自对抗 | 第五 | 第五 | 健康谎报（B）的根治手段 |
| **L5 边界层** | "可选，叙事最强" | **改判：必做，产品主线** | 首页对比视图是 90 天 M3 的载体 |
| admin 收敛 | 未定义 | **新增**：Container 删除后 admin 静态化 + 仅保留审核/导出端点 | §2.3 |

**新增工作项（本基线特有，非代码）**：

- **W1 旗舰质量攻坚**：5 个旗舰 target 的源健康排查与替换（这是"补源"，但只在核心层，且以 ok 率 ≥90% 为唯一标准）
- **W2 首个真实用户确认**：本周确定人选（§2.2 第一步动作）
- **W3 使用日志生成器**：M1 的记录工具（`docs/generated/usage-log.md` 的生成脚本）
- **W4 canonical 首页设计稿**：信息架构 + 溯源链交互（M3 前置）

**版本命名**：preview 分支的里程碑命名由产品线驱动——`preview-baseline-2026-09`（本基线）→ `preview-m1-real-usage`（M1 达成）→ `preview-m2-trustworthy-core`（M2 达成）→ …。工程层的 E 实验与 L 层继续沿用 SPEC v2 命名，两者在同一分支、同一 commit 流上并进。

## 8. 推翻规则

每条裁决的推翻条件已在其章节列出。总规则：

> **推翻裁决 = 提交证据，不是提交意见。**
